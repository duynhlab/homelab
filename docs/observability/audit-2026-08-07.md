### F-1 — Log records carry trace context as an attribute, not as trace context

**Severity: high · Owner: service repos (copied `LoggingMiddleware`) · Contract: [`observability.md` checklist](../api/observability.md#pull-request-compliance-checklist) "Exported log records carry the full LogRecord mapping (trace context, resource, scope)"**

The trace id is known at log time and *is* exported — but as a plain string in
`LogAttributes['trace_id']` instead of the OTLP LogRecord's trace-context field.

| Measured on `otel.otel_logs` | Rows |
|---|---|
| `LogAttributes['trace_id']` non-empty (a real trace id) | **33 348** |
| …of which the LogRecord `TraceId` field is **empty** | **33 327** |
| Both set | **21** |
| Field set without the attribute | **0** |

```sql
select countIf(LogAttributes['trace_id'] != '')                      attr_nonempty,
       countIf(LogAttributes['trace_id'] != '' and TraceId = '')     attr_set_but_field_empty,
       countIf(LogAttributes['trace_id'] != '' and TraceId != '')    both_set
from otel.otel_logs;
-- 33348 / 33327 / 21
```

Concrete row: service `auth`, body `HTTP request`,
attribute `cee3fc01f92a690f714d4c258504c25f`, `TraceId` empty.

**Why it matters.** The trace↔log SQL join is the stated reason RFC-0019 added
the ClickHouse sink; it works for **21 of 33 348** correlated rows. Grafana data
links keyed on the `TraceId` column are equally affected.

**The correct path already exists in-repo.** All 21 working rows are
logic-layer logs written through the context-aware logger — `Products listed`,
`Checkout confirmed`, `Item added to cart`. Only the access log, emitted by the
copied `LoggingMiddleware`, loses the context. That middleware is the component
`observability.md:147` already admits is "copied per service and drifting apart
release by release".

**Not yet established:** the exact mechanism (a `*zap.Logger` carrying a
`trace_id` *field* cannot give otelzap a span context — but which of the two
carriers each service uses needs W1 to confirm per repo).

### F-2 — Access logs include routine successful probes; 99.6% of log volume is noise

**Severity: high · Owner: service repos · Contract: [`observability.md:178`](../api/observability.md#health-readiness-and-reflection-filtering) — "Exclude routine successful probes … Skip list in the logging middleware (same list as `TracingMiddleware`)"**

On `auth`, 3 395 of 3 401 access-log records are successful probes:

| `path` | `status` | `user_agent` | Rows |
|---|---|---|---|
| `/health` | 200 | *(empty)* | 1 934 |
| `/ready` | 200 | `kube-probe/1.34` | 975 |
| `/health` | 200 | `kube-probe/1.34` | 486 |
| `/auth/v1/public/auth/jwks` | 200 | `Go-http-client/1.1` | 12 |
| real traffic (register/login/…) | — | `curl` | ~3 |

Every service sits in the same band (3 357–3 388 access-log rows in ~70 min).

**The contrast localises the defect precisely.** Metrics and traces exclude

from `LoggingMiddleware`:

```promql
# no /health or /ready among the RED route labels
/api/v1/label/http_route/values   → only real routes
```
```sql
-- probe spans among 515 total, by service
select ServiceName, count() from otel.otel_traces
where SpanAttributes['url.path'] in ('/health','/ready','/healthz','/readyz')
group by ServiceName;   -- mockpay 145, every real service 0
```

**Why it matters.** At the ClickHouse sink's **90-day** TTL this is the dominant
stored log volume, and it buries real records in every log search.

### F-3 — `OtelMetricsPipelineExportFailures` cannot fire on the first failure

**Severity: high · Owner: homelab · Same defect class as [PR #709](https://github.com/duynhlab/homelab/pull/709)**

This is the meta-alert guarding the whole metrics pipeline — its own comment
calls the push pipeline "a dependency of every alert above".

```yaml
expr: sum by (exporter) (rate(otelcol_exporter_send_failed_metric_points[5m])) > 0
for:  5m
```

| Measured | Value |
|---|---|
| `sum(otelcol_exporter_sent_metric_points)` | **211 587** → collector self-telemetry *is* scraped, so the alert's prerequisite holds |
| `sum(otelcol_exporter_send_failed_metric_points)` | **series absent entirely** |

The failure counter does not exist until the first failure creates it. #709
measured that a series born inside the window reads `1` under `increase()` and
**`0` under `rate()`** — so this expression is blind to the first failure. `for:
5m` equalling the `[5m]` window is the second, independent trap.

Consequence: if the metrics pipeline breaks, the alert that exists to say so
stays silent while every other alert quietly goes stale.

*Honest limit:* the `rate()`-vs-`increase()` asymmetry was measured on
`checkout_availability_check_total` in #709, not on this counter — nothing has
failed here yet, so both read empty today.

**Fix:** `sum(increase(otelcol_exporter_send_failed_metric_points[15m])) > 0`
with `for: 0m`, matching the four rules corrected in #709.

### F-4 — 100% of Kong's stored WARN volume is a Kong-internal deprecation notice

**Severity: medium (noise, not correctness) · Owner: homelab (collector filter) · Not a config bug**

Observed line, 348 occurrences per 3 000 log lines:

```
[kong] init.lua:904 rate-limiting: config.redis_timeout is deprecated,
please use config.redis.timeout instead (deprecated after 4.0)
```

**The platform config is correct, and identical in both codebases.** Cluster
(`kubernetes/infra/configs/kong/plugins.yaml`, both `rate-limiting-api` and
`rate-limiting-admin`) and local-stack (`local-stack/gateway/kong.yml`) each use
the nested block:

```yaml
policy: redis
redis: { host: …, port: 6379, database: 1, timeout: 2000 }
```

A repo-wide grep for the flat form (`redis_timeout`, `redis_host`, `redis_port`,
`redis_database`, `redis_password`, `redis_ssl`) across `kubernetes/` and
`local-stack/` returns **zero hits**.

**Proof that we are not the author.** Six shorthands warn, at equal frequency:

| Shorthand | Warnings | Set anywhere in the repo? |
|---|---|---|
| `redis_database` | 608 | no |
| `redis_host` | 606 | no |
| `redis_port` | 607 | no |
| `redis_ssl` | 607 | **no — never written at all** |
| `redis_ssl_verify` | 608 | **no — never written at all** |
| `redis_timeout` | 608 | no |

`redis_ssl` and `redis_ssl_verify` appear nowhere in the platform, yet warn as
often as the rest. Kong 3.9.3 materialises the full deprecated shorthand set
from the nested values during declarative-config load and warns on each
(`schema.lua:101` `shorthand_fields`, "TODO: deprecated forms, to be removed in
Kong 4.0"; each entry carries a `deprecation.message` and
`removal_in_version = "4.0"`). Context on every line is `ngx.timer` — a config
reload, not request handling.

**Impact, measured:**

```sql
select countIf(Body like '%config.redis_%') redis_shorthand, count() total
from otel.otel_logs where ServiceName='kong' and SeverityText='WARN';
-- 3840 / 3840
```

Every Kong WARN record in the 90-day store is this notice; **no real Kong
warning is present at all**. Kong's nginx error log additionally carries
`healthcheck … array headers is deprecated`, which does **not** reach the OTLP
pipeline (0 rows).

**Recommendation.** Do **not** "fix" the plugin config — it is already the
non-deprecated form, and switching to the flat keys would be a regression. Drop
the line at the collector (a `filter` processor on
`Body` matching `config.redis_% is deprecated`) so the 90-day store keeps real
Kong warnings visible, and record the reason next to the plugin config so the
next reader does not re-litigate it. Revisit at the Kong 4.0 bump, when the
shorthands are removed and the notice disappears on its own.

### F-7 — Kong's sampling rate governs the whole fleet; the services' `OTEL_SAMPLE_RATE` is inert at the edge

**Severity: high (operational surprise, not a defect) · Owner: homelab · Contract gap: [`observability.md:451`](../api/observability.md#environment-variables) documents `OTEL_SAMPLE_RATE` as "Head-sampling ratio (ParentBased(TraceIDRatioBased))" and never says the edge decides**

`pkg/obsx/setup.go:212` builds `ParentBased(TraceIDRatioBased(rate))`. ParentBased
**honours a remote parent's sampled flag**, and Kong's opentelemetry plugin
*forces* a `traceparent` onto every upstream request
(`propagation.inject: [w3c]`). So for gateway traffic the service's own ratio is
never consulted — Kong's decision is inherited wholesale.

Measured both ways on the same funnel (login → cart → session → address →
shipping → payment → confirm, all `2xx`/`201`):

| Kong `KONG_TRACING_SAMPLING_RATE` | Services `OTEL_SAMPLE_RATE` | Services with spans |
|---|---|---|
| `0.1` (deployed default) | **`1.0`** | **4** — only `auth`, `cart`, `payment`, `mockpay`; `kong`, `checkout`, `order`, `inventory`, `product` all **zero** |
| **`1.0`** | `1.0` | **13** — every service plus `kong`, `order-worker`, `checkout-worker` |

The four that appeared at Kong `0.1` did so because some of their spans are root
spans of internal paths (service-to-service and provider calls), not gateway
requests — which is the same mechanism seen from the other side.

**Consequences.**
1. Raising sampling on the services to debug a trace **does nothing** for
   requests that arrive through the gateway. The knob to turn is Kong's.
2. Conversely, `OTEL_SAMPLE_RATE=0.1` in the ResourceSets is misleading config:
   it reads like the fleet's sampling policy and is not.
3. Any runbook that says "raise the service's sample rate and reproduce" is
   wrong for edge traffic.

**Recommended:** document the precedence in the env table (Kong decides for
gateway traffic; `OTEL_SAMPLE_RATE` governs only spans a service roots itself),
and treat `tracing_sampling_rate` in the Kong HelmRelease as the fleet-level
trace sampling knob it actually is.

### F-8 — Kong's edge spans use pre-1.21 semconv while the platform pins v1.41

**Severity: medium · Owner: homelab (Kong config) / upstream Kong · Contract: [`observability.md:116`](../api/observability.md#platform-instrumentation-policy-rfc-0014--normative) "Semconv v1.41 is pinned"**

Attribute keys on a `kong` span, read from the trace store:

```
http.client_ip, http.flavor, http.host, http.method, http.route,
http.scheme, http.status_code, http.url, kong.request.id, net.peer.ip
```

Every one of those is the **old** (pre-1.21) form. The services emit the v1.41
names — `http.request.method`, `http.response.status_code`, `url.full`,
`url.path`, `server.address`, `network.protocol.version`, `client.address`.

**Why it matters.** One trace needs two attribute dialects. A TraceQL or SQL
filter on `http.request.method` silently skips the edge; a filter on
`http.method` silently skips every service. This bit the audit itself: a query
for `SpanAttributes['url.path']` on Kong spans returned nothing, which reads as
"Kong is not instrumented" rather than "Kong names it `http.url`".

**Options:** a collector `transform` processor that renames the old keys to
v1.41 on spans where `service.name == "kong"`, or accept the split and document
it next to the Kong tracing config. The rename is the cheaper fix and keeps
`docs/api/observability.md`'s pinned-semconv claim true across the whole trace.

## Kong → service trace chain, verified against the OTel specification

The user-facing question was whether tracing is correct *from Kong inward*. It
is. The requirements were taken from the OpenTelemetry specification (retrieved
via Context7: `/open-telemetry/opentelemetry-specification`, `trace/api.md`,
`context/api-propagators.md`, and OTEP-0182 *Export SpanContext.IsRemote in
OTLP*), then checked against a real `confirm` trace — **52 spans, 6 processes,
one `trace_id`** (`49008b5b…`), captured at 100% sampling.

| Specification requirement | Source | Observed |
|---|---|---|
| An entry-point span has no parent (`parent_span_id` empty) or a remote parent | OTEP-0182 | `kong` / `Server` / `kong` — **ROOT**, `ParentSpanId` empty ✓ |
| A W3C propagator must propagate a valid `traceparent`; TraceID, SpanID, TraceFlags, TraceState cross the boundary | `context/api-propagators.md` | One `trace_id` across kong → checkout → product / inventory / order → checkout-worker ✓ |
| Child spans inherit the parent's TraceId; a span created in another process has a **remote** parent | `trace/api.md` § Span Creation | `checkout` SERVER span's parent is `8e5c2be5` = Kong's `kong.balancer` **CLIENT** span ✓ — the gateway's outbound span parents the upstream's inbound span, which is the correct proxy shape |
| `SERVER` covers server-side handling of a remote request; `CLIENT` describes a request to a remote service; `INTERNAL` is an in-application operation | `oteps/trace/0059` SpanKind | SERVER at every transport-in (kong, checkout, product, inventory, order, checkout-worker) · INTERNAL for logic (`checkout.session.confirm`, `product.get_batch`, `inventory.check_availability`, `order.create`) · CLIENT for every adapter out (otelpgx `query SELECT/INSERT/BEGIN/COMMIT`, gRPC clients, `StartWorkflow`, `SignalWorkflow`) ✓ |

Chain, abridged from the captured trace:

```
kong                    Server    kong                                      ** ROOT **
├─ kong.router / kong.access.plugin.{correlation-id,cors,jwt,               Internal
│  request-size-limiting,rate-limiting,opentelemetry}
├─ kong.dns × 3                                                            Client
└─ kong.balancer                                                           Client
   └─ checkout          Server    POST /checkout/v1/private/…/confirm
      └─ checkout.session.confirm                                          Internal
         ├─ query SELECT/INSERT/UPDATE × 9                                 Client  (otelpgx)
         ├─ inventory.v1.InventoryService/CheckAvailability                Client
         │  └─ inventory Server → inventory.check_availability Internal → query SELECT × 2
         ├─ product.v1.ProductService/BatchGetCurrentPrices                Client
         │  └─ product   Server → product.get_batch          Internal → query SELECT
         ├─ order.v1.OrderService/CreateOrder                              Client
         │  └─ order     Server → order.create Internal → BEGIN/INSERT×4/COMMIT
         │               └─ StartWorkflow:OrderFulfillmentWorkflow         Client
         └─ SignalWorkflow:finalize                                        Client
            └─ checkout-worker Server  HandleSignal:finalize
```

Three properties worth calling out, because each is a place this commonly breaks:

- **The proxy hop is modelled correctly.** Kong's `kong.balancer` CLIENT span —
  not its root SERVER span — is the parent of checkout's SERVER span. That makes
  edge latency measurable as the gap between the two.
- **gRPC context survives east-west.** Each `*.Service/Method` CLIENT span in the
  caller parents a same-named SERVER span in the callee.
- **Temporal does not break the trace.** `SignalWorkflow:finalize` (CLIENT, in
  checkout) parents `HandleSignal:finalize` (SERVER, in checkout-worker) — the
  workflow boundary carries context, satisfying the worker rules in
  [`observability.md`](../api/observability.md#worker-and-temporal-instrumentation).
- **No duplicate request spans.** Each service contributes exactly one SERVER
  span plus one INTERNAL logic span, which is the contract's "do not create a
  second generic request span".

Two caveats on the same chain: it is only visible at Kong sampling 1.0 (**F-7**),
and the edge half speaks a different semconv version from the service half
(**F-8**).

## Falsified suspicions

Recorded because a suspicion that dies on inspection is worth as much as a
finding, and both of these would have shipped as false findings.

| # | Suspicion | Reality |
|---|---|---|
| X-1 | "Tempo lost the traces of 11 services" — its tag-values API returned only `auth` + `mockpay` while ClickHouse held 13 | **API artifact.** With an explicit range (`/api/v2/search/tag/.service.name/values?start=…&end=…`) Tempo returns the **same 13 services**. The block stranded by the RustFS outage retried with backoff, flushed at 16:00 and was **compacted at 16:04** — compaction only touches blocks already in the backend, so **no trace data was lost**. Operational lesson: querying Tempo tag values **without** a time range under-reports services and reads exactly like missing instrumentation. |
| X-2 | ClickHouse `StatusCode` has no `Ok` value (only `Unset` 505 / `Error` 1), so status panels must be dead | **Not a defect.** Every `StatusCode` filter across the five ClickHouse dashboards uses `'Error'`, which exists. No panel is affected. |
| X-3 | Kong's deprecation warning means the platform still uses `config.redis_timeout` | **Config is correct** — see F-4. Kong authors the deprecated fields itself. |
| X-4 | "Collector 0.158.0 refuses to start with the committed config" — `validate` errored on `service.telemetry.metrics` `has invalid keys: address`, and a 0.158.0 pod run with that config exited 1 | **My test used the wrong input.** The `address: 0.0.0.0:8888` in the HelmRelease is a **chart** value, and the chart translates it: the ConfigMap the pod actually mounts carries the modern `service.telemetry.metrics.readers: [{pull: {exporter: {prometheus: …}}}]`. The collector never sees `address`, so nothing here blocks the bump. Lesson: validate the **rendered** ConfigMap (`kubectl get cm otel-collector-opentelemetry-collector -o jsonpath='{.data.relay}'`), never the HelmRelease values. |

## Known-open, accepted (not a new finding)

- **`create_schema: true` runs DDL in the exporter's `start()`**, so an
  unreachable ClickHouse fails the whole collector at startup. `tracing-local`
  `dependsOn clickhouse-local` covers ordering but not a restart while ClickHouse
  is down. The documented mitigation (`create_schema: false` + a bootstrap Job) is
  **still untaken** — the config says so itself
  (`otel-collector.yaml:80-83`). Left as-is; changing collector startup ordering
  needs its own `make up` gate.
