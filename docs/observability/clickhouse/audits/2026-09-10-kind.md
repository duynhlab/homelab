## Scope and safety

The cluster used an isolated kubeconfig. The workstation's pre-existing
`stag` context was not changed. Runtime mutations were limited to a
`doc_audit` database on one ClickHouse replica and a PostgreSQL temporary table
inside a rolled-back transaction. A trap re-enabled merges and dropped the
ClickHouse database on success or failure.

The audit did not induce replica loss, Keeper quorum loss, disk exhaustion,
RustFS failure, read-only state, or replicated data loss. Those failure modes
have too much blast radius merely to improve an evidence label.

## Rollout evidence

`make up` created the Kind nodes, local registry, OCI artifact, and controllers.
The OpenTofu phase then revealed that its provider uses the literal default
`~/.kube/config` rather than the active `KUBECONFIG`. The audit resumed with an
explicit variable:

```bash
KUBECONFIG=/tmp/<audit>/config \
TF_VAR_kubeconfig_path=/tmp/<audit>/config \
make flux-up
```

After reconciliation:

- 30 Flux Kustomizations were Ready, with no stale observed generation.
- All three ClickHouse and all three Keeper StatefulSet replicas were Ready.
- The schema bootstrap Job was Complete before the tracing wave released.
- `platform-db`, `product-db`, and `product-db-replica` were each 3/3 Ready.
- All four Kind nodes were Ready.

The explicit variable is an audit workaround, not a committed platform change.
The bootstrap helper should propagate an isolated kubeconfig in a separate
change.

## Runtime configuration

Every ClickHouse replica returned the same MergeTree settings:

| Setting | Live value | Changed from default |
|---|---:|---|
| `parts_to_delay_insert` | 1,000 | no |
| `parts_to_throw_insert` | 3,000 | no |
| `max_parts_in_total` | 100,000 | no |
| `max_delay_to_insert` | 1 second | no |
| `merge_with_ttl_timeout` | 14,400 seconds | no |
| `max_number_of_merges_with_ttl_in_pool` | 2 | no |

This disproves the old runbook claim that the throw guard defaults to 300. The
platform's 300-part alert is an early warning: one third of the delay guard and
one tenth of the rejection guard.

The `otel` database existed on all three replicas with the expected deployed
objects:

- `otel_logs` and `otel_traces`: `ReplicatedMergeTree`, `hot_cold` policy.
- `otel_traces_trace_id_ts`: `ReplicatedMergeTree`, default policy.
- The trace-id materialized view.

After seeding 8/8 domains and running the saga/smoke traffic, every replica
converged on 225 log rows and 7,596 trace-span rows. The newest timestamps were
identical across replicas at the evidence point. These are audit counts, not
capacity or retention targets.

Every `system.replicas` row was writable, had a live Keeper session, zero queue,
zero absolute delay, and zero lost parts at the audit point.

## Parts and merge drill

The drill stopped merges only for `doc_audit.merge_lab`, inserted eight bounded
blocks, observed eight active parts, then re-enabled merges. Background work
reduced the table to one active part containing all eight rows without
`OPTIMIZE FINAL`.

The preceding 24 hours of `system.part_log` contained 13,438 `MergeParts`
events, zero failures, and a maximum recorded `peak_memory_usage` of
174.96 MiB. That live value replaces an unverified memory estimate from the
source note; it remains a point-in-time observation, not a sizing limit.

After seeded application traffic, the exporter reported 62–86 active parts per
replica and the server endpoint reported five parts in the hottest partition.
Neither alert predicate was true.

## TTL and cold-tier drills

Two independent tables separated delete and move behaviour:

1. `doc_audit.ttl_lab` used a one-second DELETE TTL and
   `ttl_only_drop_parts=1`. Materializing TTL reduced two expired rows to zero.
2. `doc_audit.cold_lab` used the deployed `hot_cold` storage policy. Its expired
   move expression changed the active part from `default` to `s3_cache`; the
   row remained queryable. The policy mapped `hot` to `default` and `cold` to
   `s3_cache`.

The first cold-tier attempt queried immediately before the background move was
visible. Repeating it with TTL metadata and a bounded wait observed the move at
the first post-materialization check. This is why an operator should check both
TTL metadata and part location instead of declaring failure from one instant.

The drill database was absent after cleanup.

## PostgreSQL adjacent audit

The deployed PostgreSQL runtime was `18.1`. A 1,000-row temporary table with a
composite `(customer_id, created_at DESC)` index produced the expected bounded
index scan and was rolled back. All three CNPG clusters stayed healthy.

The static alert-to-runbook audit found one missing deployed target,
`CNPGClusterHighReplicationLag`. A runbook was added because both generated
CNPG rule profiles still reference it. The underlying
`cnpg_pg_replication_lag` signal measures time since replay and can grow on an
idle standby, so the runbook treats byte lag and streaming state as the
authoritative impact evidence. Removing or replacing the generated source rule
belongs in a separate manifest change.

## Findings and follow-ups

| Priority | Finding | Disposition |
|---|---|---|
| P1 | Isolated `KUBECONFIG` is not propagated to the OpenTofu provider by `make up` | Follow-up in bootstrap scripts; audit used explicit `TF_VAR_kubeconfig_path` |
| P1 | `CNPGClusterHighReplicationLag` remains deployed although an older metrics doc says it was removed | Docs corrected and missing runbook added; runtime rule change deferred |
| P2 | k6 passed every assertion but could not write summaries because `scripts/k6/out/` did not exist | Evidence retained from stdout; output-directory fix deferred to test tooling |
| P2 | Collector failure counters are absent until first failure | Keep rule/runbook at `static-valid`; test only in a dedicated exporter-failure drill |

There was no P0 finding and no runtime manifest was changed in this documentation
worktree.
