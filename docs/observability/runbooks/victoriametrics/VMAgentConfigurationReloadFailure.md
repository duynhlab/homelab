# VMAgentConfigurationReloadFailure

| | |
|---|---|
| **Severity** | warning |
| **Category** | observability |
| **Source** | `.../prometheusrules/victoriametrics/vmagent-alerts.yaml` |
| **Metrics** | `vm_promscrape_config_last_reload_successful == 0` |
| **Status** | active |
| **Dashboard** | VictoriaMetrics → VMAgent |
| **Local-stack** | present |

## Meaning

vmagent rejected a configuration reload. It **keeps running on the last good
config**, which is the merciful behaviour and also the trap: scraping continues,
nothing breaks, and every change made since is silently not in effect.

## Impact

Config drift. A ServiceMonitor added an hour ago is not being scraped, and the
only sign is this alert. Because the last good config still works, no other
signal will tell you.

## Diagnosis

```promql
vm_promscrape_config_last_reload_successful
vm_promscrape_config_last_reload_success_timestamp_seconds     # how stale
time() - vm_promscrape_config_last_reload_success_timestamp_seconds
```

The reloader sidecar log names the error:

```bash
kubectl logs -n monitoring deploy/vmagent-victoria-metrics -c config-reloader --tail=50
kubectl logs -n monitoring deploy/vmagent-victoria-metrics --tail=100 | grep -i 'reload\|config\|parse'
```

The config is generated by the VM Operator from CRs, so a malformed
ServiceMonitor or VMNodeScrape somewhere in the cluster is the usual cause — and
because `selectAllByDefault` is on, *anywhere* means anywhere.

## Mitigation

1. Read the parse error; it names the offending field.
2. Fix the CR in git. Editing the generated Secret or ConfigMap is pointless —
   the operator regenerates it.
3. Confirm recovery with the timestamp metric, not with the alert clearing.

## Escalation

Warning. Escalate if the last successful reload is old — the older it is, the
more invisible drift has accumulated.
