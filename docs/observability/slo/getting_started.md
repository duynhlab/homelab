# Getting Started with SLOs

## Overview

SLOs are generated by the [`slo` Helm chart](https://github.com/duynhlab/helm-charts/tree/main/charts/slo), installed once per service as a `<service>-slo` HelmRelease. It renders a `PrometheusServiceLevel` (the Sloth Operator turns it into SLI recording rules) and a `PrometheusRule` of multi-window multi-burn-rate alerts with a minimum-events guard.

## Prerequisites

1. **Sloth Operator v0.16.0** deployed (part of `controllers-local` Kustomization)
2. **VictoriaMetrics** stack running with VMAgent (OTLP ingest) + VMSingle, and the otel-collector receiving app OTLP push
3. **Service** emitting `http_server_request_duration_seconds` over OTLP (the services deployed with the `duynh` chart do)

> The Sloth controller (`kubernetes-controller`) and the Sloth Web UI (`server`) are deployed separately — see [`README.md`](./README.md#sloth-web-ui-v0160).

## Enable SLO for a Service

### Step 1: Add the `<service>-slo` HelmRelease

The domain ResourceSet templates (`kubernetes/apps/domains/*-rs.yaml`) already
emit one for every service they template (a gRPC-only service opts out with
`slo_disabled` on its InputProvider). For a standalone service, add one next to
its workload HelmRelease, in the service's namespace:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: my-service-slo
  namespace: my-service
spec:
  interval: 10m
  chartRef:
    kind: OCIRepository
    name: slo-chart-oci
    namespace: flux-system
  values:
    service: my-service
    namespace: monitoring   # where the Sloth operator watches
    labels:
      team: platform
      env: monitoring
```

This uses the default SLO targets (99.5% availability, 95% of requests under
500 ms). To override:

```yaml
  values:
    availability:
      objective: 99.9    # stricter availability
    latency:
      objective: 99.0    # stricter latency
      threshold: "0.3"   # 300ms instead of 500ms (must be a histogram bucket)
```

### Step 2: Deploy

```bash
make flux-push && make flux-sync
```

Flux reconciles the HelmRelease, Helm renders the `PrometheusServiceLevel` CRD, and Sloth generates the PrometheusRules automatically.

### Step 3: Verify

```bash
# Check PrometheusServiceLevel was created
kubectl get prometheusservicelevel -n monitoring

# Check Sloth generated PrometheusRules
kubectl get prometheusrule -n monitoring | grep sloth

# Describe to see GEN status
kubectl describe prometheusservicelevel my-service-slo -n monitoring
# Look for: GEN OK=true

# Check SLO metrics in VictoriaMetrics (any of):
#   - http://vmui.duynh.me/vmui  (VMSingle web UI)
#   - http://slo.duynh.me        (Sloth Web UI — v0.16.0+)
# Query: slo:sli_error:ratio_rate5m{sloth_service="my-service"}
```

## Default SLO Values

Defined in the `slo` chart's `values.yaml` ([`duynhlab/helm-charts` repo](https://github.com/duynhlab/helm-charts/blob/main/charts/slo/values.yaml)):

```yaml
availability:
  enabled: true
  objective: 99.5       # 99.5% non-5xx
latency:
  enabled: true
  objective: 95.0       # 95% < 500ms
  threshold: "0.5"      # 500ms threshold
minEvents: 10           # a burn-rate arm needs this many requests in its long window
```

## How Metric Discovery Works (OTLP push)

The 10 Go services and 2 workers do not expose an application `/metrics` endpoint for scraping. Each service's OpenTelemetry SDK **pushes** metrics via OTLP to the otel-collector, which forwards them to VMAgent's OTLP ingest and on to VMSingle. VMAgent relabels the OTLP resource attributes so the series carry `app` and `namespace`:

- `service_name` → `app`
- `k8s_namespace_name` → `namespace`

No ServiceMonitor, no namespace registration, and no `app.kubernetes.io/component: api` scrape selector are involved for the app services. (VMAgent's ServiceMonitor/VMServiceScrape path still exists, but only for infra exporters — postgres, kube-state, cAdvisor, etc.)

## Verification Checklist

After enabling SLO for a new service:

- [ ] `kubectl get prometheusservicelevel -n monitoring` shows the service
- [ ] `kubectl describe prometheusservicelevel <service>-slo -n monitoring` shows `GEN OK=true`
- [ ] `kubectl get prometheusrule -n monitoring | grep sloth` shows generated rules
- [ ] VictoriaMetrics query `slo:sli_error:ratio_rate5m{sloth_service="<service>"}` returns data (via [vmui.duynh.me](http://vmui.duynh.me/vmui))
- [ ] The service appears in the **[Sloth Web UI](http://slo.duynh.me)** with both SLOs and a non-empty SLI chart
- [ ] Grafana SLO dashboards show the new service

## Troubleshooting

### PrometheusServiceLevel not created

Check that the `<service>-slo` HelmRelease was reconciled:
```bash
flux get helmrelease -n <namespace> <service>-slo
```

### GEN OK=false

Check Sloth Operator logs:
```bash
kubectl logs -n monitoring -l app.kubernetes.io/name=sloth
```

### No SLO metrics in VictoriaMetrics

Verify the service's OTLP push is landing in VMSingle (there is no scrape target to check — the app services push):

```bash
# VMSingle UI
open http://vmui.duynh.me/vmui
#   Liveness (heartbeat-absence, no up{} for pushed apps):
#     count by (app)(go_goroutine_count{app="<service>"})
#   RED base metric:
#     http_server_request_duration_seconds_count{app="<service>"}

# Confirm the otel-collector is receiving/exporting for this service
kubectl logs -n monitoring -l app.kubernetes.io/name=opentelemetry-collector --tail=50
```

Verify the service emits `http_server_request_duration_seconds`:
```promql
http_server_request_duration_seconds_count{app="<service>"}
```
