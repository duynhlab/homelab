# k6 — the assertion layer for both E2E gates

The gates used to be read by eye; now a failed row is an exit code.

| | |
|---|---|
| **Status** | In use on the Kind gate; compose rows written and contract-verified, environment untested |
| **Lives in** | [`scripts/k6/`](../../scripts/k6/) — one suite, both gates |
| **Entry point** | `make e2e GATE=kind` (or `GATE=compose`) |
| **Decision record** | [ADR-056](../proposals/adr/ADR-056-k6-e2e-assertion-layer/) |
| **Gates it serves** | [`local-stack/docs/e2e-audit.md`](../../local-stack/docs/e2e-audit.md), [`kind-e2e-audit.md`](../platform/kind-e2e-audit.md) |
| **Needs** | `k6` on PATH (v2.x); a running stack; nothing else |

## Why

Both release gates were runbooks: paste a `curl`, read the status code, tick a
box. That shape has three costs, and all three were paid.

- **Nothing returns a verdict.** A row that regresses passes by going unread.
  There was no `make` target for e2e at all, so no CI job and no exit code could
  ever depend on one.
- **Rows can be written so they cannot pass.** K4.3 drove
  `https://127.0.0.1/…` and wanted `404`. SNI may not carry an IP literal, so no
  TLS filter chain matches and the connection is dropped before HTTP happens —
  `curl` reports exit 35. The row had never passed and its failure read as a
  broken edge.
- **Whole dimensions went unmeasured.** Across 104 rows there was exactly one
  numeric threshold. No row asserted throughput, none issued two requests at
  once, and neither gate tested the edge rate limiter — while the two gates were
  configured 25× apart.

**One suite, two gates.** A unit declares a row id *per gate*, because the two
runbooks number the same assertion differently — a token mint is `A1` on compose
and `K4.5` on Kind — and some rows exist on only one side, since TLS rows are
meaningless against plain-HTTP compose. A unit with no id for the current gate is
reported as skipped, so the coverage asymmetry between the gates is a number in
the summary instead of something you notice by reading two files side by side.

**Rows become thresholds.** Every assertion is tagged with its row and every row
carries `checks{row:<id>}: rate==1.0`. A failed assertion breaches its threshold
and k6 exits non-zero. `handleSummary()` prints the PASS/FAIL table both
runbooks currently ask a human to type, and writes it to `scripts/k6/out/`.

**A row that never ran says so.** Declaring a threshold mints the submetric even
when nothing asserted against it, so zero-of-zero is reported as **DID NOT RUN**
rather than as a pass or a failure — the one outcome a green summary otherwise
cannot distinguish from success.

**PKCE is in JS, not bash.** Neither realm accepts a password grant, so every
token costs a full authorization-code round trip. Doing it in-script mints
per-VU, and avoids a trap the shell version cannot: under zsh, `USERNAME` is
already set to the OS user, so `USERNAME=alice ./keycloak-token.sh` logs in as
whoever is at the keyboard. The bash helper stays for hand-driven rows.

**Identity is modelled, not just concurrency.** Access tokens live 900s and the
services hold one active checkout session per user, so two VUs driving the same
identity evict each other and the failure surfaces as an unrelated `409`. One
identity per VU; four customer identities means four VUs is the ceiling for
order load, and that is a data constraint rather than a tuning choice.

**The funnel lives in one place.** Four scripts turn a cart into an order, and
they were four copies until one exposed a bug all four shared: creating a
checkout session answers **201 with a new session**, but **200 with the existing
one** when that identity already has an open session — the services hold one per
user as a partial unique index. So a run that leaves a session behind hands the
next run a session built from a different cart, and every price assertion after
that measures the wrong basket. It fails as "the total is not what I
engineered", which reads like a pricing bug in the platform. `lib/funnel.js`
populates the cart first and then treats a 200 as somebody else's session and
replaces it. The audit's shell rows try to guard this by probing *before*
populating the cart, which cannot work: an empty cart answers `409 Cart is
empty`, so the probe never sees the session it is looking for.

**A failing row names its assertions.** `handleSummary` replaces stdout, which
takes k6's own per-check listing with it — so the evidence table prints the names
of the checks that failed. A verdict you cannot act on is barely better than the
scrollback this suite exists to replace.

**Everything goes through the edge.** Calling a ClusterIP directly would make
load trivial and the run worthless as gate evidence:
[ADR-046](../proposals/adr/ADR-046-e2e-gate-kind-fallback/) is explicit that a
tag may never be gated on a path that skips edge policy. Pacing is therefore
bounded by the limiter, and bounded *per route* — one order costs 2 requests on
`cart` and 5 on `checkout`, so the checkout bucket is what binds.

## Operations

```bash
make e2e GATE=kind          # smoke + saga
make e2e-ratelimit GATE=kind
make e2e-load GATE=kind ORDERS_PER_SEC=2
```

Evidence lands in `scripts/k6/out/` (git-ignored) as markdown ready to paste
into a PR, plus the raw summary JSON. Add `K6_WEB_DASHBOARD=true
K6_WEB_DASHBOARD_EXPORT=report.html` for an HTML report, or
`-o experimental-prometheus-rw` with `K6_PROMETHEUS_RW_SERVER_URL` pointed at
VictoriaMetrics to keep run metrics alongside the platform's own.

### Building a Temporal backlog

`load.js` is the only way this platform has produced a non-zero
`approximate_backlog_count` — the signal the
[ADR-055](../proposals/adr/ADR-055-keda-worker-autoscaling/) KEDA scaler reads
(installed 2026-09-05). A run whose peak passes the scaler's `targetQueueSize`
of 5 should now show the versioned worker Deployment growing toward
`maxReplicaCount: 3` and returning to 1 after the 120 s cooldown — that
observation is the Kind audit row for ADR-055. Two things to know before
repeating it:

- **`kubectl scale` cannot drain a versioned worker.** Since ADR-055 two
  controllers own the count: KEDA's HPA (from the `ScaledObject` per version) and
  the Worker Controller (which floors the target version at 1). To hold a worker
  at zero for a backlog drill, pause KEDA first, then use the controller's
  managed mode, and revert both afterwards:
  `kubectl -n order annotate scaledobject --all autoscaling.keda.sh/paused="true"`,
  `kubectl -n order patch wd order-fulfillment --type=merge -p '{"spec":{"replicas":0}}'`;
  to restore: `kubectl -n order patch wd order-fulfillment --type=json -p '[{"op":"remove","path":"/spec/replicas"}]'`
  and `kubectl -n order annotate scaledobject --all autoscaling.keda.sh/paused-`.
  Leaving `spec.replicas` set is the two-writer bug `make validate` now refuses.
- **A single SKU carries finite seeded stock.** Sustained load meets
  `insufficient stock to reserve` and the saga fails — correctly, refusing to
  oversell. Past that point the run measures the inventory, not the platform.
  `saga.js` arms stock through the staff receipt endpoint for exactly this
  reason.

### Reading a failure

| Symptom | Meaning |
|---|---|
| `DID NOT RUN` | The row never executed — usually an earlier throw in the same scenario |
| `no login form for realm …` | The authorize step followed a redirect to the SPA; the VU already held an SSO session |
| `503` on `/protected/` | The service's staff JWKS is unreachable, not an identity outage — see [`api.md`](../api/api.md) |
| `429` below the ceiling | The configured number moved in `btp-api.yaml` and `config.js` is stale |
| `total is not what I engineered` | A stale checkout session was adopted — `lib/funnel.js` handles this, so suspect a script that builds sessions by hand |
| `unknown uid <name>` on a dashboard | Older boards reference a datasource by display name, which is legal; `lib/dashboards.js` counts names as live. A genuinely unknown value is a real dangling reference |

## Known gaps

- **A19's categories** — the compose runbook's own comment promises "list +
  create + the unique-name conflict", but only the list was ever coded. The k6
  port asserts what exists rather than inventing the other two; they need a
  decision, not a guess.
- **K5.7 fails on three dashboards** whose datasource references resolve to
  nothing (`flux-cluster` and `cloudnative-pg` hard-code a `prometheus` uid that
  no datasource carries; `_hAsuzBnz` names an upstream uid). The row is expected
  to fail until they are fixed — the assertion is right.
- **Compose environment untested.** Every script has been run against the
  cluster, but nothing has yet exercised local-stack's ports, plain HTTP, or its
  Grafana provisioning.
